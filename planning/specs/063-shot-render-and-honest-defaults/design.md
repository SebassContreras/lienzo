# 063 — shot-render-and-honest-defaults — Design

## Approach

- D1@1 (implements R2, R3): The camera moves out of `drawElements`, which a group calls again for its children (that is why the camera was applied once per level). It is applied per element in `drawScene`, to top-level elements only, and only when the element has `shot`. The camera is read from the element's own shot (`resolveShotCamera(shotOf(el), t)`) instead of "the active shot", so two shots overlapping in a transition each keep their own camera. Trade-off: one `save`/`restore` per shot-bound element instead of one per frame — negligible next to drawing; if a profile ever shows otherwise, consecutive elements of the same shot can share one transform. _(standard: a camera views each layer once and only layers that opt in — After Effects cameras, https://helpx.adobe.com/after-effects/using/cameras-lights-points-interest.html)_
- D2@1 (implements R1): A pure `shotTransitionAt(shot, t, sceneWidth) → { alpha, dx, scale }` in `src/engine/shots.ts` reads a shot's own transition inside the window `isElementActiveInShot` already opens: the shot enters over `[start − d, start]` and leaves over `[end, end + d]`; `fade` drives alpha, `slide` comes in from the right and leaves to the left, `zoom` grows 0.8→1 while fading. `withShotView` composes it with D1's camera inside the same `save`/`restore`. Trade-off: one fixed presentation per kind, no `direction` — the same three Remotion ships by default; `slide.direction` can be added to `ShotTransitionSchema` when someone asks. _(standard: Remotion `TransitionSeries` presentations — https://www.remotion.dev/docs/transitions/transitionseries, https://www.remotion.dev/docs/transitions/presentations/fade)_
- D3@1 (implements R4): Reproduce first: a test measures text in a plain Node ES-module process, as the CLI and the MCP server run, and compares it with the font's glyph metrics. Confirmed cause: `loadFontSync` called a global `require`, which an ES module does not have, so outside Vitest every bundled font silently fell back to the 0.54-em heuristic (narrower than the drawn text). The fix stays inside `src/engine/text-measure.ts`: Node built-ins come from `process.getBuiltinModule` and package paths from `createRequire(import.meta.url)`, so browser bundles still import nothing from Node. Trade-off: `process.getBuiltinModule` needs Node ≥ 22.3 — the project runs on Node 24 (A8). Fonts outside the bundled six still use the heuristic (unchanged; a separate follow-up if it shows up).
- D4@1 (implements R5): The defaults change where they are declared: `fill.opacity: 1` in `src/traits/fill.ts` and the path descriptor, `border.width: 0` on path, and `path` handled by `applySceneDefaults` (`src/service/compact/defaults.ts`). Because the draw-on animation (`progress`) needs a visible stroke, applying it (compact expansion or the editor's "Trazo dibujado") sets `border.width: 3` when the element has no width of its own. Trade-off: existing scenes that relied on the old defaults change look, omega-v2's `path()` among them. Mitigation: a render audit of every tracked scene and preset before and after, pinning the old values explicitly wherever the look must stay, plus a `changes.md` entry.
- D5@1 (implements R6): A pure `ignoredPaths(input, parsed): string[]` in `src/model/ignored.ts` walks the raw input and the Zod-parsed output side by side and lists the keys present only in the input. It works on plain data, so it depends on no Zod internals. It is applied where data is parsed: the tool registry adds the dropped input keys (e.g. `compact.elements.1.stroke`) to the `notices` of any tool that reports notices, `scene_build` also compares the expanded scene with its parse, and `scene_validate` reports them through `sceneNotices` (D7). Trade-off: one extra linear walk per call, small next to parsing. `z.strictObject` was rejected because it turns unknown keys into errors and would break older scenes. _(standard: Zod objects strip unknown keys by default; strict objects reject them — https://zod.dev/api#objects)_
- D6@1 (implements R7): Pure `renameAssetRefs(scene, from, to)` and `assetUsers(scenes, src)` in `src/model/asset-refs.ts` walk elements, groups and symbols for asset `src` values (image, audio, 3D, `audioTracks`). `asset_rename` and `asset_delete`, one file each in `src/service/tools/` (A20), move or remove the file through `src/service/asset-helpers.ts` and rewrite scenes with `writeJson`; the assets tab calls the same functions through the existing API. Trade-off: a rename rewrites several scene files without a transaction, so a crash midway could split references. Mitigation: scenes are rewritten first and the file moves last, and rerunning the same rename is idempotent.
- D7@1 (implements R8): A pure `sceneNotices(raw, scene, installedFonts)` in `src/service/scene-notices.ts` (ignored fields plus missing fonts, each with the top-level element it is about) is used by `scene_validate` and by the editor's "Revisión" section, which lists it under "Avisos"; clicking a notice selects its element. Trade-off: the editor's scene was already parsed when it was opened, so it shows only font notices for it — the same list `scene_validate` gives for the saved file, which the editor writes without unknown keys.
- D8@1 (implements R9): Duplicate and align recipes go in `.agents/skills/lienzo-usage/`, with no code. Trade-off: two calls instead of one; if agents keep getting them wrong, that is the signal to add a tool (YAGNI until then).
- D9@1 (implements R10): Once D1–D4 pass, the skill workarounds are reverted in `.agents/skills/lienzo-usage/` and the regression scenes are re-rendered.

## Sequencing

D1 before D2 (transitions compose with the per-element camera); D5 before D7 (the editor shows its notices); D4 together with its render audit, and both before D9. D3 starts with its reproducing test and can run in parallel.
