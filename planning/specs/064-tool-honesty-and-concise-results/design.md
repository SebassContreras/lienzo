# 064 — tool-honesty-and-concise-results — Design

## Approach

- ~~D1@1 (implements R1): the flat patch adds `borderGlow` only when the element already has one.~~ retired 2026-10-25 → D6
- D2@1 (implements R2, R3): Descriptions are edited in place. The shot rules (transition window, camera scope) are one exported string in `src/engine/shots.ts`, next to the code that implements them (063/D1, D2), used by both `shot_set` and `scene_build` — two uses, so it is shared instead of copied. The `flat` sentence lists the kinds from `FLAT_KINDS` instead of by hand. Trade-off: longer descriptions cost tokens on every tool listing; mitigation: each rule is one short sentence. _(standard: tool descriptions should state behaviour an agent cannot infer — https://www.anthropic.com/engineering/writing-tools-for-agents)_
- D3@4 (implements R4): `src/engine/text-measure.ts` exports `widthIsEstimated(style): boolean`, true when neither a canvas nor font tables measure the text — the same branch `measureTextWidth` falls through to, so they cannot disagree. a pure `estimatedWidthNotices(scene)` in `src/service/font-check.ts` gives one notice per family measured by the estimate, pointing to `scene_preview`, used by `scene_build` and `sceneNotices` (so `scene_validate` and the editor list); it is separate from the missing-font notice because a font installed with `font_install` but not bundled is still estimated, and `layoutBoxes` sets `estimated: true` on the box of a top-level `text` or `subtitles` measured by the estimate, of a group with one inside at any depth (the group's box is sized by it). A `use` is not marked: its symbol's children are listed as boxes of their own (marked when estimated) and its own box is its `w`/`h`, not measured. Both checks pass `italic` as `measureTextWidth` does; today a missing italic falls back to the upright file, so it never changes the answer, but the two calls stay identical. Trade-off: in the browser the canvas measures any font, so the flag is Node-only — exactly where the estimate is used.
- D4@2 (implements R5): `scene_build` stops returning `saved.notices`; the save notices are appended to `notices` as they are; no duplicate was ever seen (the build already expanded the animation presets the save would), so none are dropped (YAGNI). `saved` becomes the saved scene name. Trade-off: a breaking change in the output shape; mitigation: callers in this repo (tests, skills) are updated in the same task, and the MCP output schema tells clients the new shape.
- D5@1 (implements R6): `scene_build` takes `response_format: "concise" | "detailed"`, default `concise` when saving and `detailed` otherwise (with no save the scene is the only result). Concise returns `{ saved, notices, elements: [{ id, kind }] }`; `scene_get` still gives the full scene. This also removes the inert `anim.out` (kind `none`, delay 3) from what the agent reads by default; stored scenes keep it, because the schema fills it on parse anyway. Trade-off: an agent wanting the scene needs a flag or a second call; the description says so. Rejected: stripping defaults from stored scenes (touches every file and the editor for a reading problem) and a diff mode (needs a base and more code for the same gain). _(standard: `response_format` concise/detailed — https://www.anthropic.com/engineering/writing-tools-for-agents)_

- D6@1 (implements R1): `FLAT_SHAPE_PATCH` (`src/service/compact/defaults.ts`) also sets `borderGlow: { enabled: false }`. Every kind in `FLAT_KINDS` declares a border glow (the shapes share the rect fields, the path has its own), so no check is needed. A value the element writes still wins, as today. Trade-off: a kind added to `FLAT_KINDS` without a border glow would gain a field the schema drops and reports as ignored; mitigation: T001's test covers a shape and a path, and the ignored notice (063/D5) would show it at once.
- D7@1 (implements R4, R5, R6): the tool tests share one harness, `src/test/tool-harness.ts` (a fresh project in a temp folder, `call` and `ok`); `service.test.ts` uses it instead of its own copy. Trade-off: one more import for a big test file; it removes the third copy of the same setup (DRY at 2+ uses).

## Follow-up (2026-10-25)

- D9@1 (implements R8): `resolveSceneBackground` (`src/service/compact/expand.ts`) tries, in order, a background preset, then a color, then gives up with a notice pushed to the expansion's `notices`, like every other ignored input (063/D5). A color is recognised by its prefix (`#`, `rgb(`, `hsl(`); a solid background is made by the `solid` trait's own applier, so "solid" means the same here as in the editor (no gradient, dots or light). Trade-off: CSS named colors (`black`) are not recognised; mitigation: they get the notice, which names the value, so nothing is lost silently; add them when someone asks (YAGNI). _(standard: CSS color syntax — https://developer.mozilla.org/en-US/docs/Web/CSS/color_value)_
